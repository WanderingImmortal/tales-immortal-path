# Wandering Immortal — Post-stabilization architecture audit

**Baseline** — `main` at [`3c1a5b96356fde8c1240381e5da4a81431369253`](https://github.com/WanderingImmortal/tales-immortal-path/commit/3c1a5b96356fde8c1240381e5da4a81431369253), including PRs #243–#249. This review used current production paths, repository tests, and targeted in-memory probes. The probes did not change the worktree. The report distinguishes directly reproduced behavior, inspected behavior, and risks that require further measurement.

## Executive summary

The existing architecture is ready for bounded gameplay development. The shared calendar, NPC UID ownership, activity claims, and recoverable save paths now have working end-to-end tests. The remaining blockers are narrow enough to fix without another architecture pass. Complete the Category A work before broadening NPC autonomy or adding systems that multiply long-running transactions. Isolated content can ship in parallel.

The most immediate contradiction is new since succession stabilization. Ambient population retirement can mark the active player-controlled successor dead while the player continues acting. A seclusion interruption can also durably save elapsed time before earned cultivation, leaving an unrecoverable partial checkpoint if the later write fails. Manual Hall stock can train two students from one copy, and capacity rejection can consume a manual or charge for a failed purchase. A separate two-tab probe showed that ordinary autosave can overwrite a successfully saved next life.

No Critical finding was established on the supported single-tab path. The audit found no evidence for replacing the browser engine, adding another clock, or introducing a universal transaction layer.

## Verified findings

### A-01 · High · Population retirement can kill the player-controlled successor

**Evidence and impact.** `promoteAmbientToPersistent()` calls `enforcePersistentCap()`. That cap considers met persistent NPCs with no sect affiliation. `applySectSuccession()` removes the successor’s disciple affiliation and leaves the same actor in the world roster under `leaderNpcUid`. The cap then ranks this living successor as disposable and writes `alive = false` directly when their talk count is under two. A probe installed an eligible successor with one conversation and low impression, filled the cap, and ran the production retirement function. The actor became dead, living UID lookup failed, and both `gameOver` and `sectSuccessionActive` remained false. From there the player can continue with a dead world identity, and saving can write a detached player cultivation copy because the living leader lookup returns null. [ambient-npcs.js](../../ambient-npcs.js#L185) · [ambient-npcs.js](../../ambient-npcs.js#L249) · [sect-expand.js](../../sect-expand.js#L1136) · [core.js](../../core.js#L1104)

**Origin and confidence.** High, reproduced. The cap predates stabilization. The contradiction with the controlled leader follows #249.

**Smallest fix and test.** Guard the retirement decision using the existing controlled-actor and active-journey/claim queries. Keep a focused regression that promotes or retires NPCs after taking control of an eligible successor, checks actor identity across save/load, and confirms ordinary cap behavior still works. Existing unified identity tests cover normal death and succession, but do not fill the population cap. A bulk tombstone-pruning project is unnecessary for this fix.

### A-02 · High · A failed seclusion settlement write can keep elapsed time and lose its reward

**Evidence and impact.** `runPlaybackYearTick()` advances quiet time before granting progress. When a mandatory event interrupts the span, `advanceSharedWorldTime()` can save the interrupted state before returning. Playback then grants the partial-year benefit and issues a second save. A failure-injection probe allowed the interruption checkpoint and rejected every write containing the new reward. In memory the age was month 251 with 11/12 progress. The retained save and reloaded state both had month 251 with zero partial progress. The snapshot cannot distinguish this from a legitimately settled interruption. The failure is visible as a save error, but after reload the time is already spent. [advance-time-rules.js](../../advance-time-rules.js#L155) · [time-playback.js](../../time-playback.js#L79) · [core.js](../../core.js#L1095)

**Origin and confidence.** High, reproduced through the existing interruption harness with mocked circulation yield and an injected quota failure. The checkpoint ordering survives #243 and #245. This is separate from the successful partial-payout fix.

**Smallest fix and test.** Make interrupted seclusion’s elapsed time and earned payout one recoverable settlement. Prefer deferring interim ordinary checkpoints only while that settlement owns them, or add a small durable settlement receipt if an intervening mandatory checkpoint must remain durable. Preserve run-end journaling. Add a quota fault test at the exact boundary between interruption, reward, and reload. The existing 11-month test uses successful writes. [test-time-interruptions.js](../../scripts/test-time-interruptions.js#L171) · [test-save-load-reliability.js](../../scripts/test-save-load-reliability.js)

### A-03 · High · Manual copies can be duplicated in study or lost on failed delivery

**Evidence and impact.** `getDiscipleStudyBlockReason()` checks that a manual exists, and `assignDiscipleStudy()` allocates an actor slot without reserving a copy. `completeDiscipleStudy()` teaches and awards renown before requiring that a copy still exists. A level-three Hall with one copy enrolled two eligible students. Both learned the art, the final copy count was zero, and renown increased by two. Independently, `withdrawManualFromHall()` debits stock before calling `grantManual()` and ignores its result. With a full kit the action reported one withdrawn while neither store held the manual. `buyTechnique()` has the same rejected-delivery problem. A full-kit Jade purchase spent 45 stones and received no manual. The manual stock update checks the grant result after debiting currency. A nearby purchase path, `buyPill()`, also ignores a full-kit rejection from `addPill()` and advances Redwell stock after the rejected credit. That path was inspected in code. [sect-buildings.js](../../sect-buildings.js#L89) · [sect-buildings.js](../../sect-buildings.js#L144) · [sect-buildings.js](../../sect-buildings.js#L167) · [sect-buildings.js](../../sect-buildings.js#L206) · [techniques.js](../../techniques.js#L202) · [world.js](../../world.js#L723) · [actions.js](../../actions.js#L291)

**Origin and confidence.** High, all three reproduced with production Hall and purchase functions. These paths predate stabilization. #244 fixed material withdrawals, and #247 fixed conflicting claims for one student, leaving the shared-copy issue intact.

**Smallest fix and test.** Reserve one copy per active study under the current consumable-copy rule. Settle the reservation before teaching, release it on termination, and handle oversubscribed older saves deterministically without charging missing copies. Commit Hall withdrawal and market purchases only for quantities successfully credited. Preserve existing rewards, prices, and carry limits. Test two students racing for one copy, save/load with a reservation, cancellation, full kit, and successful purchase/withdrawal. The unified identity suite currently measures one successful student’s reward and #244 measures full-kit material withdrawal. [test-unified-disciple-identity.js](../../scripts/test-unified-disciple-identity.js) · [test-architecture-correctness.js](../../scripts/test-architecture-correctness.js)

### A-04 · High · A stale tab can overwrite the next life after carry consumption

**Evidence and impact.** `persistRunEndIntent()` checks the active slot’s run ID, but the ordinary `saveState()` path writes the entire snapshot without verifying its baseline. Two isolated runtimes sharing a mock storage map reproduced the risk. One completed true reincarnation and saved a new life with the 25-stone carry benefit. A stale tab then saved the old run and replaced the new slot. The legacy award remained committed. The new life and its already-consumed benefit were no longer both recoverable from storage. The same weakness can also lose progress between tabs in one life. [legacy.js](../../legacy.js#L193) · [legacy.js](../../legacy.js#L398) · [main.js](../../main.js#L801) · [core.js](../../core.js#L1095)

**Origin and confidence.** High for the reproduced sequential interleaving. Last-writer-wins predates stabilization. The legacy/receipt consequence follows #246, which documented the single-writer assumption. Simultaneous writes were not measured.

**Smallest fix and test.** Reject an ordinary save whose observed slot changed from the loaded/last-written baseline. Surface the conflict and require reload or an explicit recovery choice. Test an old runtime saving after a durable next-life write, and document the residual simultaneous read/write race if the fix is only optimistic. Use a single-writer mechanism only if browser support and usage justify it. Existing reincarnation tests share storage across sequential reloads but do not keep the previous writer live. [test-reincarnation-safety.js](../../scripts/test-reincarnation-safety.js)

### B-01 · Medium · Shared transfers and crafting have incomplete failure contracts

**Evidence and impact.** `transferFromResourceSource()` rolls stock back on a reported credit failure. An exception skips the rollback and acquisition receipt. A probe gave it a receiver that threw before credit and observed stock 6 → 5 with no receipt. Production gathering uses this adapter, but the injected exception is not evidence that the current mission receiver throws in ordinary play. The adapter also cannot infer whether a future receiver threw before or after partially crediting. Separately, `brewAlchemyPill()` and `craftGear()` check inputs before advancing time, then continue after ignoring a failed material debit. Brewing also ignores the return of `addPill()` after consuming ingredients, and forging grants success progress after the gear creation call without requiring a valid instance. These are concrete failure edges. A normal world tick that exhausts the checked inputs was not reproduced. `sellAlchemyPills()` prechecks stock and debits and credits synchronously. Residence withdrawals preflight capacity, though some ignore the final credit result. The already-fixed sect material withdrawal is a useful local precedent. [resource-sources.js](../../resource-sources.js#L635) · [resource-sources.js](../../resource-sources.js#L685) · [sect-missions.js](../../sect-missions.js#L224) · [alchemy.js](../../alchemy.js#L359) · [alchemy.js](../../alchemy.js#L431) · [crafting.js](../../crafting.js#L282) · [residence-stash.js](../../residence-stash.js#L169)

**Origin and confidence.** High for the injected adapter exception and return-value gaps. Medium for player impact in uninjected crafting. The paths predate stabilization. Scheduler quarantine in #248 makes a thrown mission step observable without reverting its side effects.

**Smallest fix and test.** When touching each route, check committed debits and credits before awarding results. Define receiver contracts before adding autonomous buyers, sellers, or producers. Test pre-credit and post-credit faults explicitly to avoid a rollback that duplicates stock. Keep abstract rewards outside conservation assertions when they are intentional. Existing source tests cover stock and explicit rejection, and disciple tests cover cargo delivery, return, and loss. They do not cover thrown receivers or completion-time craft input changes. [test-resource-sources.js](../../scripts/test-resource-sources.js) · [test-unified-disciple-identity.js](../../scripts/test-unified-disciple-identity.js)

### B-02 · Medium · NPC potential and combat use different player-relative scales

**Evidence and impact.** `getWorldNpcMaxRealm()` uses the player’s focused `G.realmIdx` for rivals and demonic talents, and procedural initialization also reads it for player-scaled roles. A probe of the same rival’s Body ceiling returned 2 before reaching Qi realm 4, 6 while focused on Qi, and 2 again when switching to unadvanced Soul. This affects eligibility for future growth. It does not erase realms already reached. `calcNpcCombatStats()` reads the NPC Qi baseline and clamps encounter health and damage against player attack/HP. That is an existing player-facing balance layer. Reusing its result for offscreen NPC-vs-NPC outcomes would make unrelated player state determine the winner. [world.js](../../world.js#L1300) · [world.js](../../world.js#L1388) · [cultivation-tracks.js](../../cultivation-tracks.js#L135) · [quests.js](../../quests.js#L166)

**Origin and confidence.** High for the reproduced ceiling and inspected encounter formulas. Both predate stabilization. #249 makes controlled NPC progression visible through the same tracks without addressing these scale choices.

**Smallest fix and test.** Before adding independent NPC rivalries or offscreen combat, distinguish intrinsic capability from player encounter tuning. Give autonomous growth a deliberate input independent of the player’s current focus, with a balance review for pacing. Preserve the current encounter tuning until that review. Add a test that switches player focus while holding the world NPC fixed. Existing tests assert that the NPC combat baseline is Qi and that highest track sets lifespan. **Origin and confidence.** High for the hidden-site code path, medium for how often unresolved origins arise. Both are integration gaps after #249. No ordinary player journey failure was reproduced.

**Smallest fix and test.** Use the player’s resolved location for the controlled actor once the inherited journey permits it. Explicitly reconcile an aborted or unresolved inherited journey before making the actor available. Add one surface-to-hidden-to-surface regression and one aborted inherited-journey case, including reload. ### B-04 · Medium · Render and post-load recovery still mutate persistent state

**Evidence and impact.** `fullRender()` initializes state, clamps Qi, synchronizes quests, reads NPC presence, and saves. The presence query calls `getWorldNpcsInZone()` → `ensureWorldNpcs()`, which can populate zones. A UI refresh can therefore affect who exists and when the world is saved. Separately, `loadState()` publishes migrated state and settles activity before `initGame()` clears orphaned combat locks and renders. A catch-up exception is logged after migration has committed. Combat cleanup and seclusion playback intentionally have different reload policies. No additional lost or duplicated reward was reproduced here beyond A-02. **Origin and confidence.** High for the coupling and sequencing. Medium for additional gameplay impact. The render side effect predates stabilization, and #245 deliberately narrowed its transactional guarantee to migration.

**Smallest fix and test.** Add explicit initialization and commit boundaries one feature at a time when working on boot, rendering, or resumable activities. Use one real browser reload scenario combining a pending decision, an existing combat lock, and an activity receipt. ## Resolved or superseded concerns

- Ordinary paid, quiet, and live time no longer use separate billing paths. Existing interruption tests verify exact deadlines, passive fractions, and normal proportional seclusion rewards. A-02 is a write-order defect.
- Legacy single-path migration no longer discards Body or Soul realms during track initialization. Full-kit sect material withdrawal keeps source stock. Bulk lifespan resolution now honors earlier breakthroughs. Keep the current regressions for these fixes.
- Unreadable ordinary or legacy saves no longer silently open a fresh creation flow and overwrite the slot. The journal and receipt protect single-writer reincarnation. A-04 is an independent stale-writer hole.
- A travelling NPC no longer appears at its destination before arrival, and a Hall student cannot begin ordinary travel. A stale zone cache does not hide a settled NPC with a valid travel location.
- The original current-timestamp scheduler starvation, fractional flooring, and silent loss of failed handlers no longer require their earlier proposed fixes. Current quarantine and explicit retry rules should remain the baseline.
- Succession no longer deletes the active leader from the authoritative roster or recreates their cultivation realms as a separate progression track. Missing deleted history in pre-upgrade saves cannot be reconstructed. The current priority is to protect the live identity from alternate writers.

## Simulation scalability

**Measured.** In a Node VM using production `tickWorldNpcGrowth(0)` and `tickAmbientNpcs(0)`, I appended synthetic dead ambient rows to the same small fixture. Each row held an ID, name, zone, state, age, and spawn time. Six batches of 120 paired calls were sampled per size. The table shows the upper median sample and the JSON character count for the whole fixture.

| Added records | Whole fixture JSON characters | 120 paired calls |
|---:|---:|---:|
| 250 | 41,633 | 7.9 ms |
| 2,000 | 296,383 | 58.4 ms |
| 10,000 | 1,464,383 | 284.1 ms |

This measures scan and serialization-size scaling for retained dead records. It excludes browser rendering, storage I/O, real NPC decisions, and elapsed-time growth. Those record counts are stress inputs rather than an observed campaign trajectory. The results establish a growing cost without establishing a current player-visible bottleneck.

**Likely future pressure.** Active journeys already have a UID index, and most autonomous decision work is localized. Ambient NPCs skip detailed cultivation, but both the ambient and growth ticks scan the roster. Presence queries can repeat population work, and a long seclusion can visit many calendar boundaries. Save size includes history and retired actors. Reincarnation replaces the active run, so ordinary NPC rosters do not accumulate across lives in the legacy record. ## Roadmap and feature readiness

### A — Fix before significant feature development

The first three actions are **protect live leader identity**, **settle interrupted seclusion atomically**, and **make manual copies and purchases conserve value**. These fixes can be developed in separate PRs. Then add the stale-writer guard before expanding the value or lifetime of persistent saves.

1. **A-01 — Retirement eligibility.** Protect the active successor first, using the existing ownership and journey checks. This establishes which identities later simulation work may retire.
2. **A-02 — Seclusion settlement.** Add the interruption/write/reload fault test and one recoverable settlement boundary. Keep ordinary save rollback and the reincarnation journal tests passing.
3. **A-03 — Manual accounting.** Reserve shared copies, settle only reserved studies, and check delivery before charging Hall withdrawals or market purchases. This is the prerequisite for adding autonomous training or more per-copy rewards. It can land in parallel with the two persistence changes.
4. **A-04 — Stale ordinary writer.** Add a conflict guard against a changed save baseline and a two-runtime regression. Keep this separate from cross-tab synchronization or a general storage redesign. It builds on the existing recovery UI and tests.

### B — Fix when touching the relevant system

- **B-01** when adding shared trade, production, or additional resource receivers.
- **B-02** before autonomous rival progression or offscreen fight results can depend on intrinsic capability.
- **B-03** before world NPCs need to locate the current leader across hidden sites or recover inherited aborted journeys.
- **B-04** when extending boot, resumable projects, or the render lifecycle. Add boundary-level browser coverage as part of that work.

### C — Defer until measurement or use makes the need concrete

Defer retired-record compaction, generic history retention, broad scan optimization, and any engine or storage migration. Preserve recovery receipts and meaningful history. Prioritize a browser profile and a representative long-run fixture over speculative loop optimization.

1. **Is it safe to resume gameplay development?** Yes. Ship bounded changes through existing authorities and complete Category A before adding significant shared-stock, long-running, or autonomous systems.
2. **What makes NPC autonomy dangerous today?** More actors competing for limited copies or stock would amplify A-03 and B-01. Autonomous behavior that retires or locates consequential actors would encounter A-01 and B-03. Player-relative ceilings and encounter tuning would leak into independent simulation under B-02.
3. **What can be built safely now?** Authored encounters, quests, locations, dialogue, and techniques using established resource and time paths. More scenarios using existing single-assignment sect missions are reasonable if they do not introduce new stock writers or mandatory handler replay. Use existing save and interruption fixtures for features that add decisions.
4. **What can wait?** A universal NPC scheduler, an economy rewrite, workers, generalized retention, and an engine migration. Introduce changes to ownership or indexing when a specific feature exposes a correctness need or real measurements establish a bottleneck.
