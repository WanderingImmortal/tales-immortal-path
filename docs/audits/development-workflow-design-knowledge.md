# Development workflow and design knowledge audit

## A. Executive summary

The repository already has a workable path from conversation to durable design, scoped issue, implementation PR, and tests. The biggest gap is the handoff between **what was decided and why**, **what code shipped**, and **what remains a viable alternative**. The same lifecycle label currently has to carry several of those meanings. A narrow change to the existing idea template and PR handoff would make decisions recoverable without adding a new tracker.

The highest-value pilot is demonic talent. Historical code and recent audits establish how the live system works. The author has now described an exploratory direction that conflicts with some of that behaviour. There is enough evidence to preserve both accounts, identify dependencies, and ask targeted design questions. There is insufficient evidence to recover the original rationale or authorize a replacement.

This audit used merged `main` at `1cbea83`, a local tree match, a sample of three Issues and older and recent PRs, repository history, and selected design, lore, code, and test references. It did not inspect complete author chats, private notes, or every issue and PR. The connector query returned no open issues in the sampled search, which establishes neither an empty private backlog nor that developers bypass the queue. This PR adds this report alone. ## D. Recommended target workflow

1. **Capture durable intent in the existing owning note.** An agent should search the topic, related code, and Issues before creating a note. Save a brief dated record when the discussion creates a reusable direction, explicit decision, or consequential fork. Record the source and whose wording it is. If the source is recollection, say so. Leave casual brainstorming lightweight.
2. **Track design disposition and implementation separately.** Use a short entry in the existing topic, with a stable heading, for each consequential decision. Record **date and source**, **scope and decision**, **why**, **alternatives and their disposition**, and **links to the implementation or verification evidence** once those exist. Use plain dispositions such as proposed, accepted, deferred, rejected, or superseded. Where useful, record the relationship separately as compatible, in tension, or contradictory. An alternative can remain valuable while incompatible with an accepted choice. Mark supersession only when an explicit decision identifies the older record and scope. Link both ways and keep the older reasoning readable. A separate implementation line can say proposed slice, prototype, partial, shipped, or drift observed. An implementation convenience gets its constraint and affected callers recorded, with a revisit trigger when known.
3. **Use the Issue for the next authorized slice.** Give it a dated design anchor, observable acceptance criteria, and dependencies. For gameplay changes, list only the affected state owners and readers, promised behaviours, compatibility requirements, and representative tests. Start with write/read boundaries such as talent → cultivation/lifespan/encounter stats, sect office → identity/settlement/calendar/save, and economy → stock source, consumer, and ledger. Check knowledge paths separately. New features can cite symbols or an owning module rather than enumerate functions. Keep `NOW.md` a short set of current links.
4. **Use a small approval boundary.** The author owns setting, characterization, world rules, and intended experience. Mechanical decisions about capabilities, progression, balance, resources, and cross-system outcomes are collaborative. Agents can choose technical representations, internal refactors, tests, and defaults that preserve established observable behaviour and compatibility. If two reasonable implementations would produce different gameplay or lore, the agent should record the conflicting evidence and ask one focused question with two options and a recommendation. Hold the affected behaviour while tracing dependencies, reproducing existing behaviour, or doing other independent work. A routine engineering constant needs approval only when it materially changes an established outcome or creates a new rule.
5. **Make the PR useful on a phone.** Lead with what changes for the player or world, the linked design decision or bug contract, evidence, and any required author decision. Put implementation detail below. On merge, update the owning note only for the affected slice, close the issue, and adjust current focus when relevant. Link to the PR and tests rather than copy their full contents.
6. **Reconcile when revisiting a system or at a short periodic review.** Start with the owning note, then follow related alternatives, closed and open Issues, merged and draft PRs, current call paths, code history, and tests. Record differences as findings with evidence and date. Classify an older option as unresolved when rejection is unverified. Confirm implementation before closing a planned item or building it again. Repair links or stale slice labels separately from any design decision. Preserve old anchors for comparison. The existing lore review and simulation audits provide the pattern. ### Review detail by change type

| Change type | Information worth putting in the PR |
|---|---|
| Small fix | Broken behaviour, expected contract, and reproduction or regression result. Mention save impact when relevant. |
| Technical refactor | Behaviour to preserve, affected entry points and tests. Note any deliberate compatibility constraint. |
| Gameplay change or new system | Accepted decision anchor, visible outcomes, cross-system and save effects, tests, and deferred assumptions. Put required author input near the top. |
| Lore or design only | Decision status, evidence, conflicting or retained alternatives, and affected owning notes. A proposal merge records the proposal's scope. |
| Prototype | Question under test, sandbox entry point, limitations, and what would qualify it for a production decision. |

### Automation and review assistance

- **Reliable automated checks.** Validate modified Markdown paths and well-defined heading links, structured fields on new decision entries if adopted, and regression scenarios for explicit invariants. Use Node for deterministic state and migration tests, Chromium for real UI and storage flows, and seeded runs for time, event order, and observable world changes. Keep link checks warning-first for historical references and treat network or permission failures as unknown.
- **Useful agent-assisted review.** List stale issue or note references, suspect repeated topics, conflicting status lines, unlinked implementation slices, and changed rules without matching test evidence. Show both sources and the exact path or diff. Verify known branch or issue status where available. Report stale priorities with the last recorded date and owner confirmation state.
- **Author judgment.** Decide whether two ideas are creatively incompatible, a lore statement is a rumour or world truth, a difference is intended or a shortcut, a gameplay invariant is still desired, or an option was rejected. Similar wording and passing tests are insufficient. ## G. Risks and tradeoffs

- **Excess documentation.** Requiring a decision record for routine fixes will bury meaningful decisions. Apply the convention to consequential rules and forks. Keep records short and use existing PRs for implementation detail.
- **Stale or conflicting authorities.** A topic note, issue, index, and PR can all disagree legitimately because each answers a different question and date. Avoid mirroring the detailed contract. Cite the scoped accepted note for intent and code plus tests for current behaviour. Preserve conflicts while they remain unresolved.
- **Agent overconfidence.** A reconstructed story can become accepted by repetition. Cite the evidence, preserve the uncertainty, and treat unknowns as unknown. Require affirmative author evidence before promoting exploratory material or declaring an old option rejected.
- **Overfitting to tests.** Scenario tests can lock in a provisional shortcut or incidental seed outcome. Assert the agreed invariant, document time mode and limits, and keep exploratory runs advisory. Preserve the useful historical test evidence when the contract changes.

## H. Author decisions required

1. Approve the small capture and escalation convention for consequential gameplay and lore decisions. Choose whether durable alternatives should be captured whenever explored or when the author marks a fork worth retaining. Agents can draft and maintain the entries.
2. When demonic talent becomes an active design topic, decide the intended meaning of the label and which behaviour belongs to intrinsic talent, public reputation, or encounter presentation. Decide what existing behaviour is temporarily retained while the design is open.
3. Before a city or cross-life redesign is queued, decide which consequences should develop independently of the player and whether any should carry between lives. Technical storage and test choices can follow those rules.
